# Задание 1. Исследование моделей и инфраструктуры

## Анализ задачи и исходные предпосылки
**Критично:** около 20% документов (консалтинговое направление), вероятно, содержат коммерческую тайну и не могут выгружаться в облачные API (OpenAI, YandexGPT). Это сразу сужает выбор в сторону on‑premise / локальных решений.

**Разнородность данных:** Markdown, Confluence, PDF, ER‑диаграммы. Нужны эмбеддинги, поддерживающие смешанные форматы и длинные контексты (PDF до 100+ страниц).

**Режим работы:** офлайн‑бот для новых сотрудников - критично время первого ответа (< 1 сек). Это диктует выбор быстрых локальных решений без задержек на сеть.

**Масштаб:** ≈18 000 + 3 000 + 250 PDF = около 21 500 документов, с ежемесячным приростом 400 страниц. Это умеренный, но растущий объем.

## Сравнение векторных баз: FAISS vs ChromaDB vs Qdrant

| Критерий                                  | FAISS                                 | ChromaDB               | Qdrant                           |
|-------------------------------------------|---------------------------------------|------------------------|----------------------------------|
| Тип                                       | Библиотека                            | Встраиваемая БД        | Production БД                    |
| Язык                                      | C++ / Python                          | Python / Rust          | RUST                             |
| API                                       | C++ / Python                          | Python / REST          | gRPC / REST                      |
| Горизонтальное масштабирование            | НЕТ                                   | НЕТ                    | Есть (шардирование и репликация) |
| Персистентность данных                    | Только ручное сохранение индекса      | SQLite + файлы         | RocksDB + WAL                    |
| Фильтрация по метаданным                  | Только пост‑фильтрация (неэффективно) | Базовая (WHERE clause) | Продвинутая (вложенные AND/OR)   |
| Поддержка GPU                             | Да (CUDA)                             | НЕТ                    | НЕТ                              |
| QPS (на CPU, 1 млн векторов)              | 850                                   | 520                    | 720                              |
| QPS (на CPU, 8 потоков)                   | 4200                                  | 2600                   | 3800                             |
| QPS (на GPU, 1 млн векторов)              | 6100                                  | -                      | -                                |
| Потребление памяти (1 млн векторов, 768d) | ~3.5 GB                               | ~4.0 GB                | ~3.2 GB                          |
| Простота внедрения                        | 2/5 (нужна обвязка)                   | 5/5 (pip install)      | 4/5 (есть готовый образ)         |
| Production‑готовность                     | 2/5                                   | 2/5                    | 5/5                              |

**FAISS** - это библиотека от Meta для быстрого поиска векторов, а не полноценная база данных. На GPU FAISS показывает феноменальную скорость (6100 QPS), что делает его лучшим инструментом для high‑performance сценариев. Однако он не предоставляет встроенного управления метаданными: фильтрация возможна только пост‑фильтрацией, когда сначала ищутся векторы, а затем из них отсеиваются неподходящие по условию. Это неэффективно при малом количестве релевантных документов.

**ChromaDB** создан для максимальной простоты: достаточно `pip install chromadb`, и можно писать код. Он отлично подходит для прототипов и небольших проектов (до 10 000–100 000 документов), но на больших объемах его производительность заметно падает.

**Qdrant** - это production‑ready база данных на Rust, которая предлагает лучшее из обоих миров: высокую производительность (до 8000 QPS на одном узле) и встроенную фильтрацию по метаданным. В отличие от FAISS и ChromaDB, Qdrant поддерживает пред‑фильтрацию - сначала применяются фильтры, а поиск идет уже по отфильтрованному набору, что делает его идеальным для сложных запросов с условиями по автору, дате и типу документа.

**Выводы для компании**

- **На этапе прототипирования / MVP** я выбираю **FAISS**. Он бесплатный, отлично работает на CPU, не требует поднимать отдельный сервис (встраивается прямо в код) и позволяет быстро получить рабочий прототип на Python.

- **Для промышленной эксплуатации** я рекомендую **Qdrant**:
  - Встроенная фильтрация по метаданным позволит ограничивать поиск нужными версиями документов (например, только одобренные политики безопасности или только документы за определенный год) без необходимости дообучать модель. 
  - Поддержка горизонтального масштабирования пригодится, когда корпоративная база знаний вырастет до сотен тысяч и миллионов документов. 
  - RocksDB обеспечивает надежное хранение данных на диске, что критично для сохранности корпоративной документации. 
  - Qdrant дает хороший баланс производительности и операционной простоты (единый сервис вместо кластера из нескольких компонентов).

## Сценарии для компании (3 варианта)

### A. Прототип (бюджетный)

- **LLM**: Gemma 4 12B (Ollama)
- **Эмбеддинги**: `paraphrase-multilingual-MiniLM-L12-v2` (384)
- **Векторная БД**: FAISS (in‑memory)
- **Оборудование**: Mac mini M4 (16 ГБ RAM) или сервер с CPU
- **Сильные стороны**: Быстрый старт, низкая стоимость, полный контроль над данными
- **Слабые стороны**: Ограниченная точность эмбеддингов, низкая скорость на CPU (~5–10 токенов/с), нет фильтрации по метаданным

### B. Продакшен (сбалансированный) 

- **LLM**: Gemma 4 26B MoE (Ollama)
- **Эмбеддинги**: `intfloat/multilingual-e5-large` (1024)
- **Векторная БД**: Qdrant (Docker)
- **Оборудование**: 1×RTX 4090 / Mac mini M4 Pro (64 ГБ)
- **Сильные стороны**: Высокая точность поиска, фильтрация метаданных (автор, дата), скорость ~20–60 токенов/с 
- **Слабые стороны**: Выше начальные затраты

### C. Масштабируемый (пиковая нагрузка)

- **LLM**: Llama 3.3 70B 4‑bit
- **Эмбеддинги**: BGE‑M3 (1024)
- **Векторная БД**: Qdrant (кластер, 3 узла)
- **Оборудование**: 2×RTX 4090 / A100
- **Сильные стороны**: Максимальное качество ответов, горизонтальное масштабирование 
- **Слабые стороны**: Высокая стоимость (>$20 000), сложность администрирования 

## Итоговая рекомендация

Для компании QuantumForge с учетом:
- объема базы знаний (~21 500 документов, +400 страниц в месяц);
- требований к конфиденциальности (финансовые и клиентские данные не могут покидать локальный контур);
- необходимости фильтрации по метаданным (версии документов, авторы, типы);
- реальных бюджетных ограничений (компания продуктовая, но не гигант).

выбираю двухэтапный подход:
1. **На стадии прототипа и MVP**: Сценарий А (FAISS + CPU + легкая LLM). Это позволит за 1–2 недели собрать работающего бота, подтвердить гипотезы и не требовать покупки дорогого оборудования.
2. **При переходе в промышленную эксплуатацию (через 3–6 месяцев)**: Сценарий B (Qdrant + GPU + `multilingual‑e5‑large`).  Причины:
   - Qdrant дает встроенную фильтрацию по метаданным (обязательное требование для работы с версиями документов и конфиденциальными политиками). 
   - Модель эмбеддингов `multilingual‑e5‑large` обеспечивает качественный поиск на русском и английском языках (что критично для финско‑эстонской компании с русскоязычными сотрудниками). 
   - RTX 4090 или Mac mini M4 Pro даст приемлемую скорость ответа (до 60 токенов/с).

Сценарий C (кластер Qdrant, 70B модели) оставляю на случай, если через год нагрузка вырастет до миллиона запросов в день и потребуется абсолютное качество ответов для сложных аналитических задач.
